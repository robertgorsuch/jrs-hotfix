# 0002: Portable archive with a jlink runtime

**Context.** jrs-hotfix needs Java 21. The hosts it runs on carry whatever Java the JasperReports Server bundle installed, usually 11 or 17, and changing that Java is not the tool's business: Tomcat runs on it. The field tests of jrsctl, the tool jrs-hotfix was split out of, showed that asking an administrator to install a second JDK first is where a first run stops; its release carried a bundled runtime for that reason. jrs-hotfix is small and has no installer, service or registry footprint of its own.

**Decision.** Each release is one archive per OS, `jrs-hotfix-<version>-linux-x64.tar.gz` and `jrs-hotfix-<version>-windows-x64.zip`, holding `bin/` (the launchers), `lib/jrs-hotfix.jar`, `runtime/` (a Temurin 21 image cut with `jlink` to the modules `jdeps --print-module-deps` finds in the shaded jar, plus `jdk.crypto.ec` and `jdk.charsets`), `README.md` and `LICENSE`. The launchers run only the bundled runtime and ignore `JAVA_HOME` and `PATH`. There is no installer and no code signing; the release publishes `SHA256SUMS` next to the archives, and the plain jar for hosts that already have Java 21. `scripts/package.sh` builds an archive and `.github/workflows/release.yml` builds, smoke-tests and publishes both on a `v*` tag.

**Consequences.** An archive is about 40 MB (38 MB for the first Windows build) where the jar alone is a few MB. A security update to the Java runtime needs a new tag: the runtime is part of the release, not of the host. Checksums prove an archive arrived intact, not who built it; signing can be added later without changing the layout. The shaded jar must not carry a dependency's `module-info.class` (picocli ships one under `META-INF/versions/9/`), or `jdeps` reads the whole jar as that module and reports only `java.base`; the shade filter removes them.
