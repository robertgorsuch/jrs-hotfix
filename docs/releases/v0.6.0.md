# jrs-hotfix 0.6.0

No ledger, and one level of undo. Support engineering found the tool clunky, and the ledger
was why: whenever the server was changed by anything else, a hotfix applied by hand or a
redeploy from a WAR, jrs-hotfix refused until `record` or `forget` made its registry true
again. jrs-hotfix is run by hand, once, in an outage window, so 0.6 reads what is installed
from the server itself, and keeps only what it needs to undo the latest apply. Download the
archive for your system below, check it against `SHA256SUMS`, and unpack it. It includes its
own Java; nothing needs to be installed. `README.md` inside the archive is the manual;
`jrs-hotfix --docs` prints it. The design is `docs/spec-no-ledger.md`.

## What changed

- **The server is the inventory.** The packages are cumulative, and the webapp states its
  build in `WEB-INF/internal/jasperserver-pro.properties`. `apply` and `verify` compare the
  package's build with it: the same build is installed already, and a newer one means the
  package would take the server back; both are refused with exit 2. An older build applies.
  A webapp that states no build is judged by its files, as before. A hotfix applied by hand,
  or a redeploy, needs nothing recorded or forgotten.
- **One level of undo.** The latest apply's snapshot, with a record of every file it wrote or
  deleted, is kept as `undo/` in the home until the next apply replaces it or a rollback uses
  it up. Every other snapshot is kept only while its run lasts, except after exit 4, which
  keeps the snapshot the operator restores from. `snapshots/` and `ledger.json` are gone.
- **`rollback` undoes the latest apply** and takes no argument. Before the service is stopped
  every file is checked against what the apply left: if the server changed since, the
  rollback is refused (exit 2) and names the files. There is no cascade; after a rollback
  there is nothing to undo.
- **`list`** shows the build the webapp states and what `rollback` would undo.
- **`runs undo <id>`** is the new name of `runs rollback <id>`, which undoes an interrupted
  run rather than a hotfix. The old name still works, unlisted.
- **`verify`** says where the package meets this site's changes whenever a baseline fits, as
  `scan --package` did, and takes `--war`. `scan` is left with one job: what the site changed.
- **`merge list`** lists the merges; `merge status` needs a merge id.
- **`--non-interactive`** is no longer listed: without a terminal nothing prompts anyway, and
  `--yes` implies it. It is still accepted.
- The menu loses "Record a hotfix applied by hand": entry 2 is "Undo the latest hotfix",
  recovery is entry 6 and settings entry 7.
- The code is smaller and simpler: the tool went from 24,100 lines to 22,900, through two
  clean-up passes (#35, #36) and the ledger's removal (#39), with the commands above added.

## What scripts must change

These are refused from 0.6.0:

| 0.5 | 0.6 | Exit |
|---|---|---|
| `record <package.zip>` | drop it: the build the webapp states is the inventory | 1 |
| `forget <id>` | drop it: there is nothing to forget | 1 |
| `rollback <id>` | `rollback` | 1 |
| `rollback ... --cascade` | `rollback`, once per hotfix to take out, while there is an undo | 1 |
| `scan --package <package.zip>` | `verify <package.zip>` (with a baseline) | 1 |
| `merge status` with no id | `merge list` | 1 |
| `apply` of a package older than the webapp's build | `rollback`, if the newer hotfix is the latest apply | 2 |

`runs rollback <id>` and `--non-interactive` keep working.

## Homes written by 0.1 to 0.5

The first command of 0.6 that changes anything converts the home once: the newest hotfix the
ledger lists as installed by jrs-hotfix, whose snapshot is there, becomes the undo; the
snapshot of a run that failed with exit 4 moves into its run directory; the other snapshots
are deleted; and `ledger.json` is kept as `ledger.json.0.5`, never read again. Read-only
commands (`list`, `verify`) read the old ledger until then and write nothing.

Finish an interrupted 0.5 job with 0.5 before you start using 0.6 if it is a rollback, or an
apply that had reached its last step: 0.6 refuses those (exit 2) and says so. An apply that
0.5 started and a crash interrupted earlier resumes or is undone with 0.6.

## Tested

`verify` green on Windows and Linux in CI for each change, the acceptance tests through the
shaded jar among them. New unit tests cover the undo store converging from a crash at every
step of keeping and using up the undo, the conversion of 0.5 homes, the build rules, the
rollback refusals (a file changed or a deleted file back since the apply, a missing snapshot,
nothing to undo) and the renamed and hidden commands. The acceptance scenarios now cover
applying two hotfixes and undoing only the later, and a redeploy after which the rollback is
refused and the package applies again.

The live sequences on the real servers, a 0.5 home converted among them, are to be run before
this is tagged; this section says what they found.

## Known limitations

- One level of undo: a hotfix before the latest apply cannot be taken out with jrs-hotfix,
  and neither can one applied by hand. Older states are a backup's job.
- A library under `WEB-INF/lib` left by a hotfix two or more back, which no readme list names,
  is deleted as superseded only when a baseline knows it; otherwise it is reported and left.
  A web fragment among them is still refused, with `baseline add` as the remedy.
- The WAR's name gives the webapp's name (`jasperserver-pro.war` or `jasperserver.war`); any
  other name is worked on as `jasperserver-pro`.
- The limitations of 0.2.1 stand.
