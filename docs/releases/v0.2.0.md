# jrs-hotfix 0.2.0

Hotfixes on customized servers. 0.1.0 replaced every file a package ships and told you which
settings to apply again by hand. 0.2.0 knows the vendor's files, so it can tell what this site
changed, keep it, and merge it with what the hotfix changes, before the outage.

Download the archive for your system below, check it against `SHA256SUMS`, and unpack it. It
includes its own Java; nothing needs to be installed. `README.md` inside the archive is the
manual; `jrs-hotfix --docs` prints it. A home written by 0.1.0 is read as it is.

## What is new

- `baseline add <jasperserver-pro.war | package.zip>`, `baseline list`, `baseline remove`:
  the vendor's files, kept in the home. The WAR the server was installed from is read as a
  stream; the baseline holds a hash for every file and the content of the ones that can be
  merged. Every apply adds the package's files as the hotfix's baseline, so the next hotfix
  is compared with them and you supply nothing.
- `scan [--package <package.zip>]`: `vanilla` or `customized: N changed, M added, K removed`,
  and the files, each with its class. Files that differ in line ends only are equal; the
  installer's files are listed and not counted; a deployed `applicationContext-externalAuth`
  context is listed under its own heading. With a package, each file it ships is judged:
  vendor change only, site change only, or a collision.
- `apply` on a server with a baseline: a file only the site changed is kept, not written; a
  properties file both changed is merged by key, a page or an XML configuration file by line;
  scripts, stylesheets and binary files both changed are replaced and listed so you carry the
  change over by hand; the installer's `context.xml` and `*-jdbc.xml` are never replaced. A
  key or a line both changed differently waits for you, and `apply` refuses with exit 2 until
  it is resolved: nothing on the server is touched meanwhile.
- `merge prepare`, `status`, `show`, `resolve --merged | --mine | --theirs`, `edit`
  (with the setting `merge.tool`), `discard`: the merge, prepared ahead of the outage and
  resolved with your own editor or tool. A merged XML file must be well-formed, must not
  define a bean, filter, servlet or listener more often than the site's file or the hotfix's
  does, and must neither bring back a bean the site removed nor lose one it added.
- `--on-conflict ask | mine | theirs | fail` and the setting `merge.onConflict`, for a
  properties key both changed. The default is `ask` at a terminal and `fail` otherwise:
  neither side wins silently.
- The plan preview lists the files merged, kept, and replaced although the site changed
  them. The ledger records the merge, the baselines, the kept files and the vendor's hash of a
  merged file; `verify` names them for an installed hotfix; a rollback brings the site's files
  back byte for byte.
- Preflight compares the build the webapp states with the ledger: the package's build with no
  installed entry is refused and `record` named; an older build than the newest installed
  entry is refused (the webapp was replaced under the ledger); a newer one is a warning.
- A library under `WEB-INF/lib` in an older version than the package brings, outside the
  readme's lists, is reported in the plan. Nothing is deleted on that ground. A file a readme
  pattern would delete that no baseline and no hotfix knows is the site's, and stays.
- The menu has eight entries; "Check the server for customizations" is entry 4 and offers to
  add the baseline when there is none.
- `runs prune` also removes merges no installed hotfix was applied with, and hotfix baselines
  older than the newest two.

## Tested on real servers

The whole sequence ran on the two JasperReports Server 10.0.0 PRO installations of 0.1.0's
tests, the Windows service and the Linux `ctlscript` one, every check green (120 on Windows,
80 on Linux): baselines from the vendor's WAR and the real package, the installed hotfix
rolled back, two site edits made (a listener in `web.xml` right where the hotfix adds three,
the session timeout, a key in `jasperreports.properties` the hotfix adds too with the other
value, and a key of the site's own), `apply` refused with both files waiting, both resolved
with `--merged`, the hotfix applied with the merge, `verify` naming `web.xml` as merged, the
hotfix rolled back with the site's files back byte for byte, and applied again.

Two things those runs taught: the vendor's own `web.xml` declares the same listener ten times
and several of its contexts define a bean twice, so the XML checks compare with both sides
rather than refusing any repeat; and Tomcat redeploys the webapp the moment `web.xml` changes,
so an edit of it while the server runs is itself an outage of a minute or two.

## Known limitations

- The merge covers files under the webapp. Files from `js-install.zip` (`buildomatic`,
  `samples`) are replaced as before, and the plan counts them.
- With a baseline for the release but none for the build the webapp states (a hotfix applied
  by hand, or by 0.1.0), `apply` is refused rather than run blind: add that hotfix's package
  with `baseline add`, or remove the baselines to apply without comparing.
- A line merge treats changes on neighbouring lines as one place, as git does: two edits need
  an unchanged line between them to merge cleanly.
- A script, a stylesheet or a binary file both changed is always the package's copy; there is
  no `--mine` for it.
- A WAR as the target (a hotfixed WAR made from a WAR, without a server) is not in this
  release.
- The limitations of 0.1.0 stand: run from an administrator prompt on Windows, set
  `service.forceStopAfterSeconds` for the script service kinds, close browser windows on the
  server during a run; JBoss, WildFly, containers and clusters are out of scope.
