# jrs-hotfix 0.9.0

What support engineering found testing 0.8.0 on a real server. The hotfix applied, the site's
changes were ported, and merges were resolved in the menu; but a WAR beside the server could not
be patched while a run on the server was interrupted, a WAR's changes could not be told from the
vendor's because its home had no baseline, a prompt did not say what it asked, and an interrupted
run could only be finished or undone. 0.9 fixes all four. Download the archive for your system
below, check it against `SHA256SUMS`, and unpack it in place of the old one. It includes its own
Java; nothing needs to be installed. `README.md` inside the archive is the manual;
`jrs-hotfix --docs` prints it.

## What changed

- **Close an interrupted run as it is: `runs abandon <id>`** (#61). For a server put right
  another way, by a restore or a redeploy, or a run that can be neither resumed nor undone any
  more. It shows the steps the run completed and those it did not, says so loudly when the run
  stopped the service and never started it again, and asks (`[y/N]`; `--yes` in a script). It
  then records the run as ended and **changes nothing else**: the server's files stay as they
  are, the run's snapshot stays for restoring files by hand until `runs prune --include-failed`,
  and the undo of the apply before it is untouched, so a later `rollback` still refuses files
  that changed since. `runs list` and `runs show` say `ABANDONED`. The menu's entry 6 offers it
  as "Close job ... (keep the server as is)", and the exit-8 message names it beside
  `runs resume` and `runs undo`.
- **A WAR's home can use the server's baselines: `baseline import <home>`** (#61). A WAR is
  worked on in a home of its own, beside it, and that home started with no baseline: `scan --war`
  said so, and **`apply --war` replaced the WAR's changes**, since without the vendor's files it
  cannot tell them apart. `baseline import <the server's home> --home <the WAR's home>` copies
  the baselines the server already has; each is built aside and renamed into place, and one the
  home already holds is left. The menu offers the copy when it picks a WAR whose home has none,
  and entry 8 gains "Its baselines". The "no baseline" message names `baseline import`.
- **The menu's WAR entries are not held up by a run on the server** (#61). Entry 8 refused to
  hotfix a WAR while a run was interrupted on the server. A WAR's home is its own: a run
  interrupted there is still refused, by the command itself (exit 8).
- **The apply options say what they are** (#61). Before an apply the menu says what the two
  choices are and what happens by default ("Older versions of libraries this hotfix replaces are
  deleted"; "when this site and the hotfix both changed the same setting, you are asked"), and
  the conflict rule is a numbered choice in plain words.
- **Every file written from an archive's names is checked to stay in its directory** (#60), by
  `compare --out`, a baseline's kept files, a distribution's root in `compare`, and a webapp
  directory's working copy. It answers CodeQL's alert #1 (`java/zipslip`); no path through the
  commands reached it, since the names were already refused before use, but each write now
  checks for itself.
- **A design for shorter output**, `docs/spec-output.md`, for support engineering to review:
  nothing about the output changes in 0.9.

## What scripts must change

Nothing. Nothing is refused that 0.8 accepted. Two commands are new:

| What | Note |
|---|---|
| `runs abandon <id>` | closes a pending run as it is; asks, or `--yes` |
| `baseline import <home>` | copies another home's baselines into this one |

A home written by 0.9 stays readable by 0.8.1: a closed run is recorded as a failed run (exit 4)
with one key more.

## Tested

`verify` green in CI, the acceptance tests through the shaded jar among them: 653 unit tests and
20 acceptance tests. New tests cover closing a run after it stopped the service (what it shows,
that nothing is touched, how it is recorded and pruned, and that the next apply runs), the
refusals without `--yes` and for an unknown or ended run; a WAR's home refused for want of a
baseline, then scanned with the server's once imported; the import copying once and leaving both
homes readable; the menu's "Close job", a WAR hotfixed while the server has an interrupted run,
the baseline offer, and the reworded prompts; and names that would escape their directory,
refused with nothing written outside.

This release was tagged without live runs on a real server, as 0.8.0 was. Support engineering's
test of 0.8.0 on a real server is what it answers.

## Known limitations

- The menu follows a waiting merge through for the server only; for a WAR, entry 8's "Its
  merges" decides the files and the hotfix is run again.
- A WAR's home is offered the server's baselines only when it is the one beside the WAR; with
  `--home`, run `baseline import` yourself.
- The limitations of 0.8.0 stand.
