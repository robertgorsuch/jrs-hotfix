# jrs-hotfix 0.8.0

The menu does everything the command line does. Until 0.7 the menu fronted seven jobs and an
apply that stopped on a waiting merge left the operator at the menu with nowhere to go; support
engineering wanted a tool driven from the menu, not one that needs the command line beside it.
0.8 adds the four jobs 0.6 and 0.7 brought (WARs, compare, merges, baselines), takes the
operator through a waiting merge to the end, and reaches every option an operator may need. It
also lets an older package be applied when the operator says so. Download the archive for your
system below, check it against `SHA256SUMS`, and unpack it. It includes its own Java; nothing
needs to be installed. `README.md` inside the archive is the manual; `jrs-hotfix --docs` prints
it.

## What changed

- **Four new menu entries** (#52). Entries 1 to 7 keep their numbers, so "entry 6" for recovery
  still holds; every entry still prints the command it runs.

  ```
    8) Hotfix a WAR or webapp directory
    9) Compare WARs, webapps, distributions or packages
   10) Merges
   11) Baselines
  ```

  Entry 8 hotfixes a WAR or a deployed webapp into a new WAR (`apply --war --out`, asking about
  `--generic` and `--install-out`), verifies a package against it, scans it, and works on the
  merges kept in the WAR's own home. Its commands run in the home the command line would use:
  `--home` if given, else `jrs-hotfix` beside the input, never the server's. Entry 9 runs
  `compare` over two or three inputs, with `--show` for one file or `--out` for a three-way
  result. Entry 10 lists the merges, then shows, decides, prepares or discards one. Entry 11
  lists, adds and removes baselines. Entry 6 adds `runs show`, and `runs prune` when nothing is
  pending.
- **The menu follows a waiting merge through** (#52). When the menu's apply stops (exit 2)
  because files of its merge wait for a decision, the menu finds that merge (by the package's
  SHA-256), lists the files, and takes each in turn: show what changed, take the merged file,
  keep the server's, take the hotfix's, or install a file you merged yourself. A merged file
  that fails its checks is asked about again; Enter stops and keeps the decisions so far, and
  entry 10 continues them. Once every file is decided the menu applies again with that merge.
- **Every option from the menu** (#52). The apply asks, only when you choose to change them,
  for `--keep-superseded` and the conflict rule (`--on-conflict`); `merge prepare` asks for
  the conflict rule; deciding a file accepts your own merged file (`merge resolve --merged
  <file>`).
- **An older package can be applied with your leave** (#52). A package older than the build
  the webapp states was refused outright, as taking the server back. At a terminal `apply` now
  asks "Apply this older package anyway? [y/N]"; in a script, the new `--allow-older` gives the
  leave. `--yes` does not: a script that ran in 0.7 is refused as before. The leave is stored
  with the run, so a resumed run rebuilds the same plan. The plan says the server is taken
  back, that files only the newer build has stay, and that a library the newer build brought
  may stay beside the package's older one; when the newer build was applied with jrs-hotfix,
  `rollback` is the cleaner way back. A package of the server's own build is still refused.
- **The scan's baseline question recommends the distribution ZIP** (#52), which covers
  buildomatic and samples too, ahead of the WAR or a hotfix ZIP.
- **Building from source checks the JDK first** (#52). A build with a JDK older than 21 now
  stops at once with "jrs-hotfix builds with JDK 21 or later; set JAVA_HOME to one", where it
  failed later in the formatter or with "release version 21 not supported". This changes
  nothing for anyone using the release archive, which carries its own Java.
- The code grew from 25,400 lines to 26,000, nearly all of it the menu.

## What scripts must change

Nothing. Nothing is refused that 0.7 accepted, and nothing is accepted that 0.7 refused unless
a script adds the new option:

| What | Where | Note |
|---|---|---|
| `--allow-older` | `apply` | applies a package older than the server's build; without it such a package is refused (exit 2) as in 0.7, with or without `--yes` |

The menu's prompts changed and new ones were added; the menu is for people, and nothing should
drive it by script.

## Tested

`verify` green on Windows and Linux in CI, the acceptance tests through the shaded jar among
them: 645 unit tests and 20 acceptance tests. New tests cover each new menu entry and the
refusals while a run is pending; the merge follow-through deciding, refusing and stopping, and
finding the merge of exactly the package applied; an older package refused with `--yes`,
applied and rolled back with `--allow-older`, and asked about at a terminal, declined and
accepted; and the leave stored with the run's arguments.

This release was tagged without live sequences on a real server, as 0.7.0 was. Nothing in it
changes how a package is applied unless `--allow-older` is given.

## Known limitations

- The menu follows a waiting merge through for the server only. When a WAR's apply waits on a
  merge, entry 8 points at its "Its merges", where the files are decided.
- Applying an older package replaces the files it ships but does not remove what only the
  newer build added; `rollback` is the way back to the build before the latest apply.
- The limitations of 0.7.0 stand.
