# jrs-hotfix 0.3.1

One fix from a field test of 0.3.0: a hotfix applied over the hotfix before it left the server
with two versions of every log4j jar, and Tomcat refused the webapp. Download the archive for
your system below, check it against `SHA256SUMS`, and unpack it; a home written by an earlier
release is read as it is.

## What happened

The package of 2026-07-30 brings log4j 2.25.4 and its readme deletes the release's 2.24.3, but
the 2.25.3 that the hotfix before it brought is named in no list, so it stayed beside 2.25.4.
Two `log4j-jakarta-web` jars are two web fragments of one name, and Tomcat refuses the whole
webapp for that: `More than one fragment with the name [log4j] was found`. 0.3.0 saw the seven
older jars and said so in the plan, but deleted nothing: that rule had been report-only until a
real package showed such a leftover.

## What changed

- A library under `WEB-INF/lib` that is an older version of one the package brings, and that
  no readme list names, is deleted as superseded when the ledger or a baseline knows it as the
  vendor's: a hotfix applied by jrs-hotfix or recorded, or the release's WAR. It goes through
  the snapshot and a rollback like any other deletion, the plan lists such libraries under
  their own heading, and `--keep-superseded` leaves them. A library nothing knows may be the
  site's own: it is reported and left, as before.
- Except when such a library is a web fragment (it holds `META-INF/web-fragment.xml`, as
  `log4j-jakarta-web` does): leaving it beside the newer one takes the server down for
  certain, so `apply` and `verify` refuse with exit 2 and say what to do.
- `verify` reads the package as `apply` does, so both say the same about superseded libraries.

## On a server with an earlier hotfix applied by hand

Make that hotfix known before applying the next one, and its libraries are deleted as
superseded: `jrs-hotfix record <earlier package.zip>` (the ledger owns its files), or
`jrs-hotfix baseline add <earlier package.zip>`. Without that, `apply` refuses a duplicate web
fragment and names the jar; remove it by hand if it is the site's own.
