# jrs-hotfix 1.0.0

Two Windows problems found on a real server on 2026-11-16, and what a review of their fixes
turned up around them. Run from the distribution's `bin\` with no settings, `settings detect`
ended with "unexpected IllegalStateException", exit 4, before it had changed anything; and an
apply's `run.log` held hundreds of lines about directories Windows will not flush. Both are fixed,
and `settings detect` now takes the run lock of the home it writes. Download the archive for your
system below, check it against `SHA256SUMS`, and unpack it in place of the old one. It includes
its own Java; nothing needs to be installed. `README.md` inside the archive is the manual;
`jrs-hotfix --docs` prints it.

## What changed

- **`settings detect` works from the distribution's `bin` folder** (#68, #69). With no settings
  and no `--home`, the home falls back to `./jrs-hotfix`, and in `bin` that is the launcher
  script, not a folder. `settings detect` writes its settings to `<installDir>/jrs-hotfix`, not
  there, so it no longer locks, creates or refuses the fallback: it finds the installation first
  and takes the run lock of the home it writes. Run from any other folder, it no longer leaves an
  empty `jrs-hotfix` folder behind either.
- **`settings detect` respects the home it writes** (#69). Where that home is not the one the
  command started in (settings found through the last home used, and detect picking another
  installation), it now stops with exit 9 while a run holds that home's lock and exit 8 while a
  run there is pending, as every other command that changes a home does. Settings that appear
  in that home after detect looked are not overwritten without `--yes`: it stops with exit 2,
  "settings exist already".
- **A home that is not a folder is exit 2, not exit 4** (#68, #69). A home that is a file, a
  dangling symbolic link, or a path below a file is refused before anything is written, with a
  remediation that names the cause: `--home` or `JRS_HOTFIX_HOME` when you set one, the
  `./jrs-hotfix` fallback when no settings were found, `jrs-hotfix` beside the WAR with `--war`.
  For the commands that change a home outside a run (`settings`, `baseline`, `merge`, `runs
  prune`, `runs abandon`), any other failure to create the run lock (no rights, a full disk) is
  exit 2 as well. Before,
  each ended with "unexpected IllegalStateException", exit 4, which means a step failed and could
  not be put back; nothing had changed.
- **Shorter run logs on Windows** (#68). Windows cannot open a directory to flush it, and every
  attempt logged an `AccessDeniedException` at DEBUG: hundreds of lines in one apply. The flush
  is no longer attempted on Windows, whose file systems journal the change themselves, and the
  log says so once. Linux is unchanged, and so are the flushes of files on both.

## What scripts must change

- The failures above exit **2**, not **4**. A script that took exit 4 from `settings detect`, or
  from any command with a `--home` that is not a folder, as "something failed part way" now gets
  the precheck code, with nothing changed.
- `settings detect` can now exit **8** or **9** for the home it writes, and **2** for settings
  that appeared there while it ran.
- The refusal reads `the jrs-hotfix home <path> is not a folder`; it read `... is a file, not a
  folder`.

No other command, option, message or exit code changed.

## Tested

`verify` green in CI on Linux and Windows, the acceptance tests through the shaded jar among
them: 667 unit tests and 20 acceptance tests. New tests run `settings detect` with no settings
and no `--home` from a folder where `jrs-hotfix` is the launcher, and from one where it does not
exist; hold the lock of the home detect writes, both when no settings were found and when they
were found in another home; write settings into that home while detect runs; give each of the
nine commands that change a home outside a run a `--home` that is a file; and give `settings
set` one that is a dangling link and one below a file.

These fixes were not run on a real server before tagging.

## Known limitations

- The limitations of 0.9.1 stand.
