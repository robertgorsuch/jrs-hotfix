# jrs-hotfix 0.5.0

Two decisions the 0.2 design had left open, now made and built. Download the archive for
your system below, check it against `SHA256SUMS`, and unpack it. It includes its own Java;
nothing needs to be installed. `README.md` inside the archive is the manual; `jrs-hotfix
--docs` prints it. A home written by 0.1 to 0.4 is read as it is.

## What is new

- **Keeping the site's copy of a script, a stylesheet or a binary file.** When both the site
  and the hotfix changed such a file, the hotfix's copy landed and the plan listed the file for
  you to carry your change over by hand; those classes are never merged by line, because they
  are build output or binary. That is still the default. Now `jrs-hotfix merge resolve
  <mergeId> <path> --mine` keeps the site's copy instead: the file is not written, it is
  listed as kept in the plan and the ledger with the note that the hotfix's change in it is
  not installed, and a rollback is unaffected. `--theirs` confirms the default; `--merged` is
  refused for these files with the reason. A kept jar is yours to answer for: the hotfix's
  jars are a set, and the kept one is not part of it.
- **A baseline that does not fit says which libraries differ.** A release baseline is used
  only when at least 95 in 100 of the jars it lists are in `WEB-INF/lib` unchanged. The
  refusal used to give the number alone; it now names the first five differing jars, each
  `absent` or `differs`, and how many more, and the remediation says that a library the site
  itself removed or replaced counts against the fit. Dozens differing means the WAR is
  another cut or edition; one or two means the site dropped a driver. The threshold itself
  stays: it has met two servers, both at 100 in 100 against the vendor's WAR.

## Tested

`verify` green on Windows and Linux in CI, the acceptance tests through the shaded jar
among them. New unit tests cover the fit message, `--mine`, `--theirs` and the refused
`--merged` on a script in the merge workspace, and an apply that keeps the site's script
and records it as kept by the operator. The live sequences on the real servers were not
rerun: `apply` without a resolution behaves exactly as 0.4.0.

## Known limitations

- `record` on the server that deploys a hotfixed WAR reads the files: the ledger there learns
  the hotfix and its hashes, not which files were merged.
- The WAR's name gives the webapp's name (`jasperserver-pro.war` or `jasperserver.war`); any
  other name is worked on as `jasperserver-pro`.
- The limitations of 0.2.1 stand.
