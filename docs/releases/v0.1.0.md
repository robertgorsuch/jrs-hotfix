# jrs-hotfix 0.1.0

The first release. jrs-hotfix applies, verifies, records and rolls back official Jaspersoft
cumulative hotfix packages on JasperReports Server 10.x running under Tomcat, on Windows and
Linux. It is the hotfix job of jrsctl, split out into a tool of its own: the same snapshot,
service stop, idempotent steps, resumable runs and per-file rollback, without the REST client,
the database, the signed bundle format and the rest jrsctl carried.

Download the archive for your system below, check it against `SHA256SUMS`, and unpack it. It
includes its own Java; nothing needs to be installed. `README.md` inside the archive is the
manual; `jrs-hotfix --docs` prints it.

## What it does

- `apply <package.zip>`: nine steps. Preflight, snapshot of every file the package replaces
  or deletes, staging, service stop, per-file swap, JSP cache removal, service start, wait
  for the server, ledger entry. `--plan` shows the plan and stops.
- `rollback <id>`: puts the snapshot back, newest hotfix first when several own the same files
  (`--cascade`).
- `verify <package.zip>`: whether the package is readable and applies here, and what it would
  change.
- `list`, `record`, `runs` (resume or undo an interrupted run, prune old ones), `settings`.
- A menu at a terminal; subcommands for scripts.

Service kinds: Windows service, systemd, the vendor's `ctlscript`, Tomcat's `catalina`
script, or manual.

## Tested on real servers

Before this release the tool applied the cumulative hotfix `20260730_0457` to two real
JasperReports Server 10.0.0 PRO installations, rolled it back and applied it again, every
check green: a Windows service on the build machine, and a Linux installation controlled by
`ctlscript.sh`. Both keep the ledger, the snapshots and the run records under
`<installDir>/jrs-hotfix`.

## What those tests changed

- A hotfix whose files are already all in place is refused with exit 2 and the advice to
  `record` it, instead of an outage that changes nothing.
- The installer's values in `js.quartz.properties`, `js.jdbc.properties`,
  `hibernate.properties` and `keystore.init.properties` survive a hotfix: the package's file
  is merged with the server's by key. The plan names the keys it kept, never the values.
- The JSP cache is removed after the swap and after a rollback, as the vendor's readme
  requires.
- The readme's manual steps are carried whole and as written; SQL that repeats a line is no
  longer mangled.
- `list` and the menu show the build the webapp states about itself.
- The plan preview counts files by area and action instead of listing twenty paths.
- The wait after the start sends one request and lets it wait, because Tomcat answers every
  request held during deployment at once, and a burst of those hit a race in the server's
  cookie filter that left it answering HTTP 500 until a restart.
- The preflight probe of `baseUrl` waits up to a minute; a healthy server took over ten
  seconds for one answer.
- On Linux the installation was detected as its Tomcat directory when the running Tomcat's
  `catalina.base` was looked at first; the parent that holds `buildomatic` or `ctlscript` is
  now the installation.
- When a stop times out with the JVM still ending, the undo of that stop waits for the JVM
  once more and then starts the service; before, it saw the JVM "running", left it, and the
  server was down once the JVM had ended. A JVM that never ends is reported, and the run
  ends with exit 4 so the operator looks.
- Only a JVM (or `jsvc`) whose command line names `catalina`, or Tomcat's Windows service
  wrapper, counts as a Tomcat. Before, any process did, and a force stop on the Linux test
  machine ended the operator's own shell, whose command line named the install directory
  and `work/Catalina`.

## Known limitations

- Windows: run it from an administrator prompt when the files are owned by
  `BUILTIN\Administrators`, which is what the bundled installer leaves. Preflight refuses
  otherwise, before anything is changed.
- Script service kinds (`ctlscript`, `catalina`): the vendor's stop script gives Tomcat ten
  seconds and gives up; the hotfixed 10.0.0 JVM on the Linux test machine did not end for
  minutes after that. Set `service.forceStopAfterSeconds` (60 worked there) so the tool ends
  the JVM that outlives the script; without it a stop fails after
  `service.stopTimeoutSeconds` and the run is undone.
- The four merged settings files have no common ancestor, so where both the server and the
  package have a key the server's value stays. Compare the keys the plan names if a fix
  depends on the package's value. `META-INF/context.xml` is replaced like any other file.
- The Community edition's webapp states no build stamp, so `list` shows none for it.
- Files under `buildomatic` and `samples` that hold settings are replaced; the plan counts
  them.
- The vendor's cookie filter race (a shared date format in `HttpOnlyResponseWrapper`) is in
  the server, not in this tool: a burst of simultaneous requests at the moment the server
  starts can still trigger it from any client. Close browser windows on the server during a
  run.
- JasperReports Server under JBoss or WildFly, containers and clusters are out of scope.
