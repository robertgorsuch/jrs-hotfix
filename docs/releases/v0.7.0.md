# jrs-hotfix 0.7.0

Customizations wherever a hotfix goes. Until 0.6 jrs-hotfix kept a site's changes in the
webapp of a running server, and nowhere else: buildomatic's files were replaced as the package
had them, a WAR was the only offline target, and a build host that deploys with buildomatic
could not be hotfixed at all. 0.7 applies the same rules to the installation tree, to WARs and
deployed webapps, and to a build host, and adds `compare` for the questions support asks before
a hotfix. Download the archive for your system below, check it against `SHA256SUMS`, and unpack
it. It includes its own Java; nothing needs to be installed. `README.md` inside the archive is
the manual; `jrs-hotfix --docs` prints it. The design is `docs/spec-targets.md`.

0.6.0 was not released on its own: if you are coming from 0.5, read its notes
(`docs/releases/v0.6.0.md`) too, for the ledger's removal and the commands it changed.

## What changed

- **buildomatic and samples are kept and merged like the webapp** (#42, #47, #48). Given a
  release baseline made from the vendor's distribution (`jrs-hotfix baseline add` with its ZIP
  or directory), `scan` lists what the site changed under `buildomatic/` and `samples/` in a
  section of its own, and `verify`, `merge prepare` and `apply` judge those files by the same
  rules as the webapp's: kept, merged by key or by line, or waiting for a decision. The files
  written for one site are never replaced: `default_master.properties`,
  `keystore.init.properties`, `bin/js-import-export.sh` and the sample data sources under
  `install_resources/export/js-catalog/`; a properties file among them is merged by key with
  what a hotfix adds. What buildomatic builds or logs (`build_conf/`, `logs/`, `js-mvn`,
  `conf_source/iePro/lib/iecp.jar`) is counted, not listed. Without such a baseline,
  buildomatic's files are replaced as before, and the plan says so.
- **A build host can be hotfixed** (#46). A build host holds the unpacked distribution
  (`buildomatic/`, `samples/`, `jasperserver-pro.war`) and deploys to servers elsewhere.
  `settings detect` in that directory recognizes one and writes settings with `service.kind`
  `none`. `apply` then hotfixes the WAR beside itself, checks it entry by entry, swaps
  buildomatic's files in place and only then puts the new WAR in place of the old one; nothing
  is stopped or started. The old WAR moves into the home, not copied, and is the undo with the
  installation files: `rollback` puts both back, and refuses if the WAR changed since the apply.
  Deploying is the operator's: the plan ends by naming `js-ant deploy-webapp-pro`, which
  jrs-hotfix never runs.
- **`--war` takes a deployed or exploded webapp directory** (#44), which is read and never
  written: `apply --war <dir> --out <out.war>` gives a WAR that carries this site's
  `META-INF/context.xml`, `*-jdbc.xml` files and installer-written settings, merged with the
  package's as on a server. `scan`, `verify` and `merge prepare` take a directory too.
- **`apply --war ... --generic`** (#44) writes the vendor's copies of those files instead, for
  an environment that deploys one generic WAR with its own database configuration. Every other
  change of the site is kept or merged. It needs a release baseline, and the plan lists the
  files it takes from the vendor.
- **`apply --war ... --install-out <dir>`** (#46) also applies the package's buildomatic and
  samples files to an installation tree kept elsewhere, merged with the site's when the home
  has the distribution as a baseline, after a snapshot; `rollback --home <home>` puts them
  back. An empty or absent directory receives them as the package has them. It needs a home of
  its own: the home of a server or a build host is refused (exit 2).
- **`compare <a> <b> [<c>]`** (#45) reads any of a WAR, a webapp directory, the vendor's
  distribution, an official hotfix package, or `server`, and changes nothing. Two inputs list
  the files that differ or are in one only; three (base, mine, theirs) say for each file
  whether mine changed it, theirs did, or both, merged as `merge` merges or a conflict.
  `--out <dir>` writes the three-way result, with conflict markers; `--show <path>` prints one
  file's differences. It exits 0 when the inputs are the same and **7**, a warning, when they
  differ or conflict.
- An installer-written script or binary that a hotfix ships is now kept, with the hotfix's copy
  in the merge workspace as `theirs`, as an installer-written XML file already was (#47).
- Homes made for WARs have `service.kind` `none` too, so their rollback has no service step;
  settings written for WARs by an earlier release are rewritten so the first time `--war` uses
  the home.
- The code grew from 22,900 lines to 25,400 for the four targets above and `compare`.

## What scripts must change

Nothing is refused that 0.6 accepted. Two things are new to a script:

| What | Where | Note |
|---|---|---|
| exit 7 | `compare` only | the inputs differ, or a three-way comparison has conflicts; a finding, not a failure |
| `service.kind` `none` | `settings show`, `settings.json` | a build host, or a home made for WARs |

A server whose home has a distribution baseline will see buildomatic's changed files in `scan`
and `verify`, and an apply may now wait for a decision on one of them (exit 2) where 0.6
replaced it.

## The design's open points

Two facts were measured on a real 10.0.0 installation before this release: buildomatic deploys
the distribution's own `jasperserver-pro.war`, unzipped straight into the application server
(`deploy-webapp` in `buildomatic/bin/app-server.xml`); and the files a site writes under
buildomatic are the ones listed above, found by extracting the vendor's buildomatic from the
10.0.0 installer and comparing it byte for byte with an installation's.

## Tested

`verify` green on Windows and Linux in CI for each change, the acceptance tests through the
shaded jar among them. New tests cover a build host applied and rolled back in place, with no
WAR left in the home after; the site's buildomatic and WAR changes merged against a
distribution baseline; the WAR put back when the apply fails after replacing it; a rollback
refused after the WAR changed; `--install-out` and its refusal in a server's home; directory
inputs and `--generic`; `compare` two-way and three-way over every kind of input; and the
installer-written files kept when a package ships them.

The live sequences on a real server and a real build host are to be run before this is
tagged; this section says what they found.

## Known limitations

- jrs-hotfix never runs buildomatic: on a build host, deploying the hotfixed WAR, and after a
  rollback the earlier one, is the operator's.
- A build host is recognized by the WAR at the distribution's root; a tree built from source,
  which deploys from `buildomatic/install_resources/war/`, is not one.
- `compare` reads a WAR or package into a temporary directory first, so it needs free space
  for the larger input under the system's temporary directory.
- The limitations of 0.6.0 stand.
