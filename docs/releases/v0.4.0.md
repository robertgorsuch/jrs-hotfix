# jrs-hotfix 0.4.0

A smaller tool. Nothing was added; four things that nothing needed were taken out, so there
is less to read, less to run and less to go wrong. Download the archive for your system
below, check it against `SHA256SUMS`, and unpack it. It includes its own Java; nothing needs
to be installed. `README.md` inside the archive is the manual; `jrs-hotfix --docs` prints
it. A home written by 0.1 to 0.3 is read as it is.

## What went, and why

- **The record beside a hotfixed WAR.** `apply --war` wrote `<out.war>.jrs-hotfix.json`
  next to the output; nothing ever read it. What it held is elsewhere: the output WAR's own
  `WEB-INF/internal/jasperserver-pro.properties` states the build, the hotfix baseline in
  the home holds the package's files, the merge holds the site's, and `runs/<runId>/plan.json`
  holds what every file became. The output is now the one file written outside the home.
  A `.jrs-hotfix.json` left by 0.3.x beside a WAR can be deleted.
- **`merge edit` and the setting `merge.tool`.** The three sides of a file that needs a merge
  are plain files in the workspace, `merges/<mergeId>/files/<path>/base|mine|theirs`, so any
  merge tool can be pointed at them, and `merge resolve <mergeId> <path> --merged` records
  the result as before. A `settings.json` that still holds `merge.tool` loads; the key is
  ignored, and `settings set merge.tool` is refused as unknown.
- **The pager, `--no-pager` and `--ascii`.** `--docs` and `merge show` print at once; pipe
  them to `more` or `less` for a screen at a time. The status words are still the glyphs
  (`✔ ✖ ↻ ↩`) when the output encoding can carry them and the ASCII words (`OK`, `FAIL`,
  `RETRY`, `UNDO`, `SKIP`) when it cannot, as on cmd.exe; that choice was always automatic,
  and the flag only forced it.
- **The Windows registry scan in detection.** `settings detect` no longer runs `reg.exe`
  over the Uninstall keys. The candidates are the running Tomcats and the well-known
  directories under `C:\Jaspersoft` and Program Files, which is where the bundled installer
  puts a server, and any other path can be typed.

A script that passes `--no-pager` or `--ascii`, or runs `merge edit`, must drop them: 0.4.0
refuses them as unknown with exit 1.

## Also since 0.3.1

The README was rewritten in the shape of jrsctl's (a table of jobs, a numbered quick start,
common jobs, the exit codes with what to do), and a wiki with the same structure is at
https://github.com/robertgorsuch/jrs-hotfix/wiki. The README's "Supported" line now says
which exit code refuses what: a package for another release is exit 2, a file that is not a
package or a WAR that is not a 10.x webapp is exit 6, and the Community edition is out of
scope.

## Tested

`verify` green on Windows and Linux in CI for each change, the acceptance tests through the
shaded jar among them. No behaviour of `apply`, `rollback`, `record`, `forget`, `verify`,
`scan`, `baseline` or `merge prepare|status|show|resolve|discard` changed; the 0.2 and 0.3
live sequences on the real servers were not rerun for this release.

## Known limitations

- `record` on the server that deploys a hotfixed WAR reads the files: the ledger there learns
  the hotfix and its hashes, not which files were merged.
- The WAR's name gives the webapp's name (`jasperserver-pro.war` or `jasperserver.war`); any
  other name is worked on as `jasperserver-pro`.
- The limitations of 0.2.1 stand.
