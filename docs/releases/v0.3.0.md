# jrs-hotfix 0.3.0

A WAR as the target. 0.2 kept and merged a site's changes on a running server; 0.3.0 does the
same to a WAR file, without a server, for sites that build or deploy their webapp from one.

Download the archive for your system below, check it against `SHA256SUMS`, and unpack it. It
includes its own Java; nothing needs to be installed. `README.md` inside the archive is the
manual; `jrs-hotfix --docs` prints it. A home written by 0.2 or 0.1 is read as it is.

## What is new

- `apply <package.zip> --war <in.war> --out <out.war>` makes a hotfixed WAR from a WAR and
  touches no server: no service, no snapshot, no rollback. Five steps: preflight (the WAR's
  release, edition and build fit the package, the output is absent, there is room), stage,
  assemble (the input streamed to a temporary file without the entries the package replaces
  or deletes, the staged files appended), check (every written entry hashed, every dropped
  entry absent, the entry count), and the rename beside the record `<out.war>.jrs-hotfix.json`.
  The input is never modified; the output is never overwritten.
- `scan --war <file.war>` and `merge prepare <package.zip> --war <file.war>` read the site's
  files from the WAR, so what 0.2 does on a server it does to a WAR: files only the site
  changed are kept, properties files are merged by key, pages and XML by line, and what
  waits for you waits in the same workspace, resolved with the same commands. A merge
  prepared for the WAR is what `apply --war` uses, by itself or with `--merge <mergeId>`.
- The home is `--home` (or `JRS_HOTFIX_HOME`), else `jrs-hotfix` beside the WAR. The
  release's baseline goes into that home with `baseline add`, which works there before any
  `--war` command. Every `apply --war` writes the hotfix's baseline, so the output WAR, given
  as the next input, is compared with the hotfix's files. The WAR is unpacked under
  `<home>/wars/` while it is worked on, one at a time; that copy may be deleted at any time.
- Files of `js-install.zip` (`buildomatic`, `samples`) are not part of a WAR: the plan says
  how many were left out, and they are applied on the server the WAR is deployed to. A WAR
  is not a server's inventory: `apply --war` writes no ledger entry; the sidecar is the
  record, and the deploying server learns the hotfix through `jrs-hotfix record` there.

## Tested

`verify` green on Windows and Linux: 604 unit tests and 20 acceptance tests through the
shaded jar, the new one making a hotfixed WAR from a customized WAR beside a running stand-in
server that is never touched. Against the real 10.0.0 WAR and the real package of 2026-07-30,
no server involved: a site WAR with the scheduler filled in and a key of its own added,
`baseline add`, `scan --war --package` naming the one collision, `apply --war --out` in two
minutes with both properties files merged automatically, the output holding 5844 entries
(5819 less 149 deleted plus 174 added, as the check step counts) with the site's key and the
vendor's new keys in it.

## Known limitations

- `record` on the server that deploys a hotfixed WAR reads the files, not the sidecar: the
  ledger there learns the hotfix and its hashes, not which files were merged.
- The WAR's name gives the webapp's name (`jasperserver-pro.war` or `jasperserver.war`); any
  other name is worked on as `jasperserver-pro`.
- The limitations of 0.2.1 stand.
